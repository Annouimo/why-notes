# why-notes

通过设计可探索的数学与物理讲义来学习。

这个项目探索一套将大语言模型纳入学习过程的方法：围绕一个具体问题，亲自组织解释、推导和可视化，制作一份自己能够对其内容负责的网页讲义。在制作中发现理解的缺口，通过查证、讨论和练习修正，再用独立解释与解题检验学习效果。

目前进入第一篇讲义的制作阶段：**如何理解一致连续**。已实现 Astro + MDX 静态站点、七个函数例子的小框交互，以及数学行为检查。讲义仍为草稿，正在制作分支中审阅。

## 为什么做这个项目

项目式学习提供了一个具体成果，让探索、实践和反馈有明确的落点。对于数学与物理基础理论，这个成果可以是一份讲义：要把知识讲清楚，就需要决定从哪里出发、哪些条件不可省略、推理如何衔接，以及什么例子能够暴露误解。

希望借鉴 3Blue1Brown 的解释方式：让读者看见关系、理解构造，并将直觉与公式连接起来。成品采用网页，以便自由跳读、反复比较、局部修改和传播。

这个项目同时探索两个问题：

- 怎样通过设计讲义，获得更深、更持久、能够迁移的理解？
- 怎样与 AI 协作，减少实现负担，同时保留学习者自己的思考与判断？

这套方法的效率需要实际检验。讲义制作得精美，并不自动意味着知识已经掌握。

## 成品：可以操作的解释

每篇讲义围绕一个明确问题，结合文字、公式、静态图和必要的交互，让读者掌握阅读速度。

例如，“为什么知道两个基向量的去向，就知道整个二维线性变换？”比“线性代数基础”更适合作为一篇讲义的起点。它有明确的解释目标，也容易设计对应的推导、图示和检验题。

### 阅读原则

- 使用清晰的标题、目录和段落链接，方便跳读与回看。
- 正文保留完整的解释路径；补充证明、背景和更多例子按需展开。
- 关键状态直接可见，便于前后比较；动画支持暂停、回放和重置。
- 交互具有明确目的：帮助读者观察关系、作出预测、验证猜想或寻找反例。
- 同时考虑桌面与触摸设备，不依赖悬停才能获取重要信息。
- 重要图示提供可阅读的静态状态，便于归档与回顾。

直观与严格需要衔接。图形展示的是现象、直觉还是证明，应当说明；定义、适用条件与关键推理不能被动画替代。

## 怎样设计一篇讲义

开工前先回答：

1. **核心问题**：这篇到底解释什么？
2. **前置知识**：读者需要已经知道什么？
3. **学习目标**：读完后，读者应该能够独立解释、预测或完成什么？
4. **范围边界**：哪些相关问题暂时留给其他讲义？

下面的结构是一份设计检查表，可以按主题调整：

| 环节 | 任务 |
| --- | --- |
| 起点 | 提出一个具体问题，说明它为什么值得解释 |
| 预测 | 让读者根据已有认识先作判断 |
| 构造 | 用尽量简单的对象建立模型 |
| 关键转折 | 找出让问题变得容易理解的关系 |
| 形式化 | 将直觉连接到定义、公式与推导 |
| 边界 | 说明适用条件，用反例检验说法 |
| 迁移 | 用变化题检查是否能够独立应用 |

主线之外的新问题先记录下来，再判断是否值得单独展开，避免一篇讲义无限扩张。

## 原稿与生成方式

希望维护可读、紧凑、便于审阅的原稿，通过构建工具生成网页。

原稿的紧凑主要来自复用高层组件：讲义中写明要展示的数学对象、关系和操作，组件负责绘图、布局与交互细节。

| 层次 | 保存的内容 |
| --- | --- |
| 讲义原稿 | 正文、公式、讲解顺序、例子、图示参数、练习与引用 |
| 可视化组件 | 绘图、参数联动、动画、触摸与键盘操作 |
| 发布系统 | 页面布局、目录、链接与构建流程 |

最终发布的文字应完整保存并经过审阅。简短的设计提纲可以用于讨论，但不能替代已经确认的正文。重要的设计意图、尚未解决的问题和查证依据也应保留，便于继续学习与修改。

### 技术路线

首篇采用 **Astro + MDX + TypeScript + SVG**：

- **MDX**：在 Markdown 正文中嵌入组件，作为讲义原稿格式。
- **Astro**：组织页面并构建网站，让正文以静态内容为主，局部加入交互。
- **SVG**：优先尝试二维几何、向量和少量对象的可视化。
- **Canvas 或三维工具**：在大量绘制或空间操作确有必要时再引入。
- **Manim**：按需评估其在特殊动画素材制作中的作用。

Idyll 等交互式文章工具也值得参考。初期先复用现有工具；从多篇讲义中识别稳定需求，再决定是否需要专门的原稿语法或生成器。

### AI 与构建的边界

AI 生成或修改的正文、例子和组件，先保存为可审阅的修改；接受后才成为正式源文件。

构建过程忠实转换已确认的源文件，不在每次构建时调用大模型重新扩写讲义。在固定源文件、依赖与构建配置下，发布内容应保持稳定。

## 怎样与 AI 协作

人负责解释的逻辑与正确性，AI 协助探索、质疑和实现。

| 环节 | 学习者的工作 | AI 的工作 |
| --- | --- | --- |
| 初始理解 | 尝试独立解释，标出不确定处 | 通过追问帮助发现缺口 |
| 探索与查证 | 阅读可靠资料、推导并判断 | 提出不同解释、定位资料、寻找反例 |
| 讲义设计 | 选择主线，决定关键措辞 | 提出候选结构，说明各自取舍 |
| 制作 | 编写或确认核心原稿 | 提议例子、局部改写，编写组件 |
| 审阅 | 检查数学、文字与页面效果 | 提交差异，说明依据和未决问题 |
| 学习检验 | 关闭讲义，独立解释与解题 | 提出变化题，针对错误反馈 |

AI 提供的例子同样需要检查。数值正确、例子典型、能够支持论点，是不同的要求。

### 修改与审阅

初步采用小范围分支与 Pull Request：

- 每次修改集中解决一个解释问题，或实现一个组件。
- 提议说明改了什么、为什么修改、依据是什么，以及哪里仍不确定。
- 审阅同时查看文字差异和页面预览。
- 核心论证应能由学习者独立重述或推导；存在疑问的内容明确标记。
- 可视化按数学模型检查，包括边界情况、单位与适用的守恒关系。
- 查证时记录实际使用的教材章节、论文或网页；AI 的回答用于讨论，不能代替依据。

需要保留亲自组织解释的过程。仅仅觉得 AI 写得合理，还不足以判断自己已经理解。

## 如何判断是否学会

每篇讲义除了页面验收，还需要学习检验：

1. **独立解释**：关闭原稿，能否重建核心关系与推理？
2. **说明边界**：能否说清适用条件，并解释反例为什么成立？
3. **迁移应用**：更换数字、情境或问题表述后，能否继续解答？
4. **延迟保持**：隔几天再回来，能否重新解释和应用？

同时记录制作时间、主要理解缺口和仍然会犯的错误。如果大量时间用于界面微调，而知识理解没有相应进展，就缩减制作范围。

## 运行与制作

需要 Node.js 24（CI 使用同一版本）。

```sh
npm ci
npm run dev
```

本地预览包含草稿，默认地址以终端输出为准。

| 命令 | 用途 |
| --- | --- |
| `npm run check` | Astro / TypeScript 检查与数学行为测试 |
| `npm run build:preview` | 构建包含草稿的预览，页面带 noindex |
| `npm run build` | 正式构建，排除草稿及其 URL |
| `npm run pack:preview` | 构建并打包供 Cloudflare 连接上传的测试 Worker |
| `npm run preview` | 在本地查看 dist 构建产物 |
| `npm run new:note -- topic-slug "标题"` | 新建正文与制作说明，不覆盖已有主题 |

`dev` 使用 `--ignore-lock` 保持前台运行，方便由预览服务管理进程，避免 Astro 在识别到编程助手后自行转入后台。

### 内容放在哪里

- `src/content/notes/<slug>/index.mdx`：唯一正式正文源，元数据包含标题、摘要、日期、分类和 draft。
- `docs/briefs/<slug>.md`：教学设计、交互要求、数学约定和未决问题。
- `src/components/`：可复用的页面部分。
- `src/lib/`：交互代码与独立数学计算。
- `tests/`：关键行为和边界条件。
- `AGENTS.md`：编程助手的实现、审阅和发布约定。

首页及讲义路由由内容文件自动生成。新主题默认 `draft: true`，预览可以访问，正式构建不会生成该主题页面。数学公式在构建时渲染，字体和脚本随站点分发。

### 一篇讲义的工作流

探索理解 → 整理制作说明 → 在制作分支实现 → 打开预览并审阅 → 用户确认发布 → 合并 main 并部署。

你负责解释目标、关键体验与最终数学审阅；助手负责整理说明、实现、适配和预先验证。正文只维护一份，制作说明保存设计意图，不重复抄录正文。

### 部署状态

目标是独立 Cloudflare Worker 与 `learn.annouimo.com`，仓库为唯一源码。初始制作预览使用 **`why-notes` 本身的原生 Version URL**，只上传版本，不创建正式部署：

- [站点预览](https://uniform-continuity-why-notes.keen18906416.workers.dev/)
- [一致连续：前两幕](https://uniform-continuity-why-notes.keen18906416.workers.dev/notes/uniform-continuity/)

正式域名绑定与 Git 自动发布连接在正式发布前完成。当前预览通过 `npm run pack:preview` 生成自包含的版本包，由已授权的 Cloudflare 连接上传到 `why-notes` 的 `/versions` 接口，附带 `workers/alias=uniform-continuity`。它包含 WOFF2 字体，页面及响应均禁止索引。预览功能已开启，正式 workers.dev 入口保持关闭，尚无正式部署。正式站点使用 Workers Static Assets 托管完整 `dist/`。

当前已包含 GitHub Actions 检查；这不等于已经配置 Cloudflare 自动部署。后续连接应保证：制作分支构建包含草稿的预览，main 构建正式站点。每次新增讲义无需重新配置域名。
